# Google Drive 동기화 설계

> 상태: 설계안 (코드 변경 없음). 2026-11-11 기준 v2.0.0 코드를 조사해 썼다.
> 이미 정한 방향은 "정한 것"에 모았다. 13장의 질문은 2026-11-11에 모두 답을 받았다.

## 0. 정한 것

- 설정 → "동기화" 탭의 **"Google 계정 연결"** 버튼을 누르고, 브라우저에서 허용만 하면 된다. 다른 프로그램은 설치하지 않는다.
- 개발자 서버는 없다. 메모는 사용자 본인 Google Drive의 **appDataFolder**에만 둔다. 사용자는 이 폴더를 Drive 화면에서 볼 수 없고, 다른 앱도 읽을 수 없다.
- 권한 범위는 세 개다. 모두 비민감 범위다.
  - `https://www.googleapis.com/auth/drive.appdata`: 앱 전용 공간 읽기·쓰기
  - `openid`, `https://www.googleapis.com/auth/userinfo.email`: 연결한 계정 이메일 확인(6.4)
  - Cloud 콘솔 → Google 인증 플랫폼 → 데이터 액세스에서 `openid`와 `.../auth/userinfo.email`을 추가한다(`drive.appdata`는 이미 있다).
  - 앱이 요청할 때 보내는 문자열: `openid https://www.googleapis.com/auth/userinfo.email https://www.googleapis.com/auth/drive.appdata`
- 로그인은 데스크톱 방식이다. 브라우저를 열고 loopback(`http://127.0.0.1:<임의 포트>`)으로 돌아오며, **PKCE(S256)**와 `state` 검사를 함께 쓴다.
- 클라이언트 ID와 비밀값은 설치본에 들어가므로 비밀로 보지 않는다. 보호는 PKCE가 맡는다.
- OAuth JSON은 저장소에 커밋하지 않는다. .gitignore에 걸린 위치에 두고, 빌드할 때만 설치본에 넣는다.
- refresh token은 keyring에 둔다(서비스 이름 `memo_slide_sync`, AI 키 `memo_slide_ai`와 분리). access token은 메모리에만 둔다.
- "연결 끊기"를 누르면 keyring의 토큰을 지우고, Google에 토큰 철회(`POST https://oauth2.googleapis.com/revoke`)도 보낸다.
- Google 검수 없이 production으로 게시했다(2026-11-11 기준 완료, `drive.appdata`는 비민감 범위로 등록됨). 도메인은 나중에 붙이고, 그때 앱 코드를 고치지 않아도 되어야 한다(→ 9장).
- 블로그 링크는 설정 상수 한 곳에서 관리한다. 블로그는 `https://nursecoder.vercel.app`, 개인정보처리방침은 `/tools/slide-memo/privacy`다.

## 1. 지금 저장 구조 조사 (v2.0.0)

| 항목 | 지금 방식 | 동기화에 주는 영향 |
|---|---|---|
| 메모 ID | `memos.id INTEGER PRIMARY KEY AUTOINCREMENT`. PC마다 1, 2, 3…으로 매긴다 | **PC끼리 겹친다.** 전역 고유 ID(`uid`, UUID4)가 필요하다. 로컬 `id`는 그대로 두고 화면·버전 테이블 연결용으로만 쓴다 |
| 시각 | `datetime.now().isoformat(timespec="seconds")`. 로컬 시각, 시간대 없음, 초 단위 | PC 시계가 다르거나 시간대가 다르면 비교할 수 없다. **순서 판정에 쓰면 안 된다**(→ 3장 HLC) |
| `updated_at`이 바뀌는 때 | `db.update()` 하나뿐이다. 제목·본문 자동 저장(`save_now`), **색 변경**(`_on_color_changed`), 글꼴 변경 | 고정(`set_pinned`), 휴지통 이동(`soft_delete`), 복원(`restore`)은 `updated_at`을 바꾸지 않는다. 동기화는 `updated_at`이 아니라 필드별 기록으로 판정해야 한다 |
| 이전 버전 | `memo_versions(id, memo_id→memos.id, title, content, created_at)`. `save_now` 직전에 `snapshot()`, 5분 간격, 메모당 20개, 하드 삭제 때 CASCADE | PC마다 따로 쌓인다. 충돌에서 진 쪽을 여기에 넣으면 된다(`snapshot(force=True)`와 같은 길) |
| 휴지통 | `deleted_at`에 로컬 시각. 30일 뒤 `cleanup_old_trash`가 하드 삭제. "영구 삭제"와 "휴지통 비우기"는 `db.delete` + `_delete_memo_images` | 휴지통 이동과 복원은 상태 필드로 전파한다. 하드 삭제는 별도 기록(purge)이 필요하다 |
| 고정 | `is_pinned` 0/1 | 독립 필드로 전파한다 |
| 색 | `color`에 프리셋 이름 또는 `#RRGGBB`(`normalize_color`). `color_before_v2`는 2.0 이전 색 백업 | `color`는 전파한다. `color_before_v2`는 로컬 이주용이라 전파하지 않는다 |
| 사용자 지정 색 | `settings["user_slots"]` | 전역 설정 하나로 전파한다(질문 3) |
| 글꼴 | `font_family`, `font_size`(메모별) | 전파한다 |
| 이미지 | `~/.memo_slide/images/img_<YYYYmmdd_HHMMSS_ffffff>.png`. 본문 HTML에 **절대 경로**(`<img src="C:/Users/<이름>/.memo_slide/images/...">`)로 들어간다 | **다른 PC에서는 경로가 깨진다**(사용자 이름이 다름). 올릴 때는 경로를 내용 해시 표지로 바꾸고, 받을 때는 그 PC의 경로로 되돌린다 |
| 설정 | `settings(key, value)` | 대부분 PC별 설정이다(→ 5장) |
| 스키마 | `PRAGMA user_version = 3`. 이주 전에 `memos.db.bak`을 한 번 만든다(같은 이름으로 덮어씀) | 동기화 이주는 v4로 올리고, 백업 이름을 따로 둔다(→ 11장) |

정리하면, 동기화에 꼭 필요한 변경은 다음 세 가지다.

1. 메모에 전역 고유 ID `uid`를 붙인다.
2. 시각 대신 HLC로 순서를 정한다.
3. 이미지 경로를 PC와 무관한 표지로 바꾼다.

## 2. Drive 저장 구조

appDataFolder 안의 파일은 모두 평평하게(폴더 없이) 이름으로 구분한다.

| 파일 | 쓰는 쪽 | 내용 |
|---|---|---|
| `dev_<device>.json` | 그 PC만 | PC 이름(사용자가 볼 이름, 예: "회사 노트북"), 마지막 동기화 시각(`last_sync`, 바뀐 게 없어도 1시간마다 다시 씀), 압축본·로그 조각 목록, 다른 PC를 어디까지 받았는지(`cursors`), 너무 커서 못 올린 그림(`too_big`) |
| `log_<device>_<n>.jsonl` | 그 PC만 | 변경 기록(op)을 한 줄에 하나씩 적는다. `n`은 그 조각의 첫 순번(압축 뒤에도 이름이 겹치지 않는다) |
| `snap_<device>_<n>.json` | 그 PC만 | 압축본. 그 PC가 쓴 op 중 필드별 최신 것만 남긴다(→ 2.3) |
| `alive_<device>.json` | 그 PC만 | 그 PC에 있는 메모 uid 목록(휴지통 포함). 바뀔 때만 다시 쓴다. 오래 꺼져 있던 PC가 돌아올 때만 읽는다(3.6) |
| `img_<sha256>.png` | 누구나 (내용이 같으면 이름도 같다) | 이미지 원본. 한 번 올라가면 내용이 바뀌지 않는다 |

`<device>`는 처음 연결할 때 만드는 무작위 ID(UUID4 앞 12자)다. 로컬 `sync_state`에 저장한다.

### 2.1 원칙: 한 파일은 한 PC만 쓴다

- `log_`, `snap_`, `dev_` 파일은 이름에 들어간 PC만 만들고, 고치고, 지운다. 다른 PC는 읽기만 한다. 그래서 두 PC가 같은 파일을 동시에 쓰는 일이 없다.
- `img_` 파일은 이름이 내용 해시라 누가 올려도 내용이 같다. 두 PC가 동시에 올려도 같은 이름의 파일이 둘 생길 뿐 내용은 같다(Drive는 이름 중복을 허용한다). 읽을 때는 아무거나 하나 쓰고, 중복은 압축 때 하나만 남긴다.

### 2.2 op 형식 (log 한 줄)

```json
{"id":"a1b2c3d4e5f6:1042","hlc":"1762851234567.0003.a1b2c3d4e5f6","uid":"5b0c…","f":"body",
 "v":{"title":"장보기","content":"<p>우유 <img src=\"smimg:9f86d0….png\"></p>"},
 "base":"0f1e2d3c4b5a:88"}
```

- `id`: `<device>:<순번>`. PC 안에서 1씩 늘어나고 다시 쓰지 않는다. 같은 op를 두 번 받아도 `id`로 걸러낸다.
- `hlc`: 순서 판정용 시계(→ 3장).
- `uid`: 메모 전역 ID. 전역 설정이면 `settings:user_slots`처럼 쓴다.
- `f`: 필드 묶음. 묶음마다 따로 "마지막에 쓴 쪽이 이긴다"를 적용한다.
  - `body`: 제목과 본문. 둘을 함께 묶는다(제목만 섞이면 이상하다)
  - `color`
  - `font`: 글꼴과 크기
  - `pin`
  - `trash`: 휴지통에 넣은 시각(로컬 표시용) 또는 null
  - `created`: 처음 만든 시각(표시·정렬용)
  - `purge`: 직접 영구 삭제(값 없음)
  - `autopurge`: 30일 자동 비우기(값 없음, `base`=근거가 된 `trash` op). `purge`와 따로 둔다. 같은 필드면 되살림으로 무효가 된 자동 비우기가 직접 삭제를 덮거나 다음 자동 비우기를 막는다(2단계 시험에서 찾음)
- `base`: 이 PC가 이 필드를 덮어쓸 때 알고 있던 직전 op의 `id`. 충돌을 알아보는 데 쓴다(→ 3장).

### 2.3 로그 조각과 압축

- Drive는 파일에 덧붙이기가 안 된다. 그래서 "현재 조각" 파일을 통째로 다시 올린다(`files.update`).
  - 조각이 **500줄 또는 1MB**를 넘으면 다음 번호로 새 조각을 연다. 이렇게 하면 한 번에 올리는 크기가 1MB를 넘지 않는다.
- 압축은 자기 PC 것만 한다(`engine.compact`, 6단계). 조각이 **20개 이상이거나 합계 5MB 이상**이면, 또는 영구 삭제한 메모의 본문을 Drive에서 지워야 하면 다음 순서로 진행한다.
  1. 자기 op 중 `(uid, f)`마다 최신 것만 남기고(로컬 `sync_outbox`도 같이 줄인다) `snap_<device>_<n>.json`으로 올린다. 이 파일에는 "순번 ≤ N까지 포함"(`upto`)이라고 적는다.
  2. `dev_<device>.json`이 새 snap을 가리키고 조각 목록은 비운다. 로컬 상태도 같은 트랜잭션에서 바꾼다.
  3. 그다음에 이름에 자기 device가 들어간 옛 조각과 옛 snap을 모두 지운다.
  - 2에서 꺼지면 dev 파일은 옛 조각을 그대로 가리킨다. 3에서 꺼지면 옛 파일이 남을 뿐이고 다음 압축이 치운다. 읽는 쪽은 PC별 순번 커서로 중복을 거르므로 결과가 같다(`test_sync_compact.py`에서 두 곳 모두 멈춰 봄).
- **영구 삭제한 메모 잊기** (`store.forget_deleted`, 동기화 때마다)
  - 직접 영구 삭제: 바로 `sync_head`와 내 기록의 본문을 비우고(id·시계만 남김) 압축을 예약한다. 다음 압축에서 Drive의 내 파일에서도 사라진다. 다른 PC가 그 메모를 고친 적이 있으면 그 PC도 자기 파일을 같은 방식으로 비운다.
  - 자동 비우기: 되살림에 대비해 7일 뒤에 비운다(3.4).
  - 둘 다 **180일**이 지나면 그 메모의 기록을 통째로 잊는다. 이 PC가 쓴 기록과 `sync_head`, Drive의 압축본 모두에서 지운다. 그보다 오래 꺼져 있던 PC는 3.6으로 처리한다.
  - 로컬 DB 파일의 빈 공간에는 SQLite 특성상 지운 내용이 한동안 남을 수 있다. 메모를 지울 때도 지금 앱과 같은 동작이다.
- 그림 정리는 압축과 따로, 하루 한 번 한다(3.5 "안 쓰는 그림 정리").

### 2.4 읽는 쪽

- 로컬 `sync_cursor(device, applied_seq)`로 다른 PC마다 어디까지 적용했는지 기억한다.
- 받을 때:
  1. 다른 PC의 `dev_` 파일을 읽어 조각 목록을 얻는다.
  2. 아직 안 읽은 조각과 snap만 받는다.
  3. `순번 > applied_seq`인 op만 적용한다.
- 압축으로 중간 조각이 사라졌으면 snap부터 읽는다. LWW 적용은 같은 op를 여러 번 해도 결과가 같아서(멱등이라) 문제없다.
- **모든 PC의 새 op를 먼저 모은 뒤, HLC 순서로 한 트랜잭션에 적용한다**(커서 갱신 포함). body의 `base` 사슬도 적용 전에 모두 넣는다.
  - PC별로 차례로 적용하면, 오래 꺼져 있던 PC가 "A가 B의 수정 위에 이어 쓴 op"를 B의 op보다 먼저 받는다. 그러면 사슬이 끊겨 거짓 충돌로 판정된다(4단계 설계 중 찾음).
- 조각 파일이 아직 안 보이면 그 앞까지만 적용하고, 그 PC의 `dev_` 파일은 다음에 다시 읽는다(순번 구멍을 만들지 않는다).
- 망가진 줄은 버린다. 같은 PC가 그 순번을 다시 쓰지 않으므로 그 op 하나는 빠진다. 다만 다음 차이 맞추기에서 그 PC가 같은 필드를 다시 고치면 맞춰진다.
- 다른 계정으로 연결하거나 Drive를 지워 기록을 비울 때는 **device ID도 새로 만든다**. 같은 ID로 순번을 1부터 다시 쓰면, 옛 계정 Drive의 같은 순번 때문에 다른 PC가 새 op를 "이미 받음"으로 거른다.

## 3. 합치기 규칙

### 3.1 시계: HLC (Hybrid Logical Clock)

- HLC는 `(벽시계 ms, 카운터, device)` 세 값으로 이뤄진다. 매기는 방법은 다음과 같다.
  - 이 PC에서 op를 만들 때: `l = max(l, now_ms)`. `l`이 그대로면 카운터를 하나 올리고, 커졌으면 카운터를 0으로 둔다.
  - 다른 PC의 op를 받을 때: `l = max(l, 받은 l, now_ms)`로 맞추고 카운터도 따라 올린다.
  - 비교는 `(l, 카운터, device)` 사전순으로 한다.
- 이렇게 하면 다음이 보장된다.
  - **원인과 결과가 뒤집히지 않는다.** B가 A의 수정을 받은 뒤 고친 내용은 PC 시계가 몇 시간 늦어도 항상 A보다 뒤로 판정된다.
  - 둘 다 오프라인이라 서로 모르고 고친 경우(동시 수정)에는 시계가 맞으면 실제로 나중에 쓴 쪽이 이긴다. 시계가 틀려도 모든 PC가 같은 쪽을 고른다(결과가 갈라지지 않는다).
- 이 방식의 한계: 시계가 크게 앞선 PC는 동시 수정에서 계속 이긴다. 다만 진 쪽 내용은 지워지지 않고 이전 버전에 남는다.
  - 받은 `l`이 지금보다 **1일 넘게 앞서면** 로그에 경고를 남긴다. 시계를 끌어올리는 것은 막지 않는다. 막으면 순서 보장이 깨진다.

### 3.2 필드 묶음별 마지막 쓴 쪽 승리 (LWW)

로컬 `sync_head(uid, f) → (op_id, hlc)`로 필드마다 지금 이긴 op를 기억한다. 받은 op `r`은 다음과 같이 처리한다.

1. `r.hlc ≤ head.hlc`이면 진 op다.
   - `f == body`이고 `r.base`가 head의 조상이 아니면(동시 수정) **진 내용을 이전 버전에 넣고** 충돌 토스트를 띄운다.
   - 그 밖의 경우는 무시한다.
2. `r.hlc > head.hlc`이면 이긴 op다. 적용하고 head를 바꾼다.
   - `f == body`이고 `r.base != head.op_id`이면(동시 수정) **지금 로컬 내용을 이전 버전에 넣고** 충돌 토스트를 띄운다.
   - `r.base == head.op_id`이면 그냥 이어 쓴 것이라 충돌이 아니다.
   - "조상" 판정에는 `sync_body_chain(uid, op_id, base)` 기록을 쓴다. 이 기록은 받은 `body` op마다 남기고 압축 때 정리한다. `base`를 따라 올라가 보고, 기록이 끊겨 알 수 없으면 동시 수정으로 본다.
   - 버전에 넣을 내용이 지금 내용이나 최근 버전과 같으면 넣지 않고 토스트도 띄우지 않는다. 다른 PC의 op가 순서가 뒤바뀌어 도착했을 때 거짓 충돌이 나는 것을 막기 위해서다.
3. `color`, `font`, `pin`, `trash`는 조용히 LWW만 적용한다.
   - 그래서 한 PC가 고정하고 다른 PC가 본문을 고쳐도 둘 다 반영된다(필드가 다르므로).

두 PC 모두 같은 판정을 하므로, 양쪽 모두 이긴 내용이 화면에 나오고 진 내용은 이전 버전에 남는다. **어느 경우에도 쓴 글이 사라지지 않는다.**

- 이전 버전에 넣을 때는 `memo_versions`에 `created_at`=지금, 제목은 원래 제목을 그대로 둔다.
  - 버전 목록에서 구분되도록 표시 열을 하나 두는 것도 검토했지만 하지 않기로 했다. 대신 토스트에서 "이전 버전"을 연다.
- 이전 버전 자체는 동기화하지 않는다(질문 1).

### 3.3 지금 열려 있는 메모

- 받은 op가 지금 편집 중인 메모의 `body`를 바꾸면, 먼저 `save_now()`로 로컬 수정을 op로 만든 뒤 적용한다.
  - 그러면 위 판정이 그대로 동작한다. 로컬이 진 경우 그 내용은 이전 버전으로 간다.
- 적용 뒤 에디터를 다시 불러온다. 커서 위치는 같은 글자 위치(넘치면 끝)로 되돌린다.
- 휴지통 미리 보기 중에는 에디터에 쓰지 않는다. 기존 `_trash_preview_id` 규칙을 그대로 따른다.

### 3.4 삭제와 복원

- 휴지통 이동과 복원은 `trash` 필드 op 하나로 전파한다.
  - 다른 PC에서도 휴지통으로 가고, 복원도 그대로 전파된다.
  - `trash` op의 값에는 **휴지통에 넣은 시각 `trashed_at`**(그 op를 만든 PC의 HLC 벽시계 값, UTC ms)을 담는다. 모든 PC가 같은 값을 갖는다.
  - 로컬 `deleted_at`은 `trashed_at`을 이 PC 시간대로 바꿔 적는다(표시와 정렬용).

#### 휴지통 자동 비우기 (30일)

PC마다 따로 날짜를 세면 한 PC에서 되살린 메모를 다른 PC가 지울 수 있다. 그래서 다음처럼 바꾼다.

- **기준 시각**: 동기화된 `trashed_at`이다. 받은 시각이나 로컬 `deleted_at`이 아니다.
- **지울 조건**: 아래가 모두 맞아야 지운다.
  1. 이 PC 시계로 `now ≥ trashed_at + 30일`이다.
  2. 그 메모의 `trash` head가 여전히 그 op다. 그 사이 되살림(`trash=null`)이나 다시 휴지통에 넣은 일이 없다는 뜻이다.
  3. 그 op보다 HLC가 큰 `body`, `color`, `font`, `pin` op가 없다. 휴지통에 있는 동안 고친 일이 없다는 뜻이다.
- **지울 때**: `autopurge` op를 만들고 `base`(지운 근거가 된 `trash` op id)를 붙인다. 같은 휴지통 기간에는 한 번만 만든다.
- **받는 PC**: 받은 PC도 같은 세 조건을 **자기 시계로** 다시 확인한다.
  - 1번이 아직 아니면(시계가 늦은 PC) 자기 시계가 `trashed_at + 29일`에 이를 때까지 적용을 미룬다. 시계가 크게 앞선 PC 하나가 모두의 휴지통을 일찍 비우지 못하게 하기 위해서다. 하루는 PC 간 시계 차이를 봐준 여유다.
  - 2번이나 3번이 깨졌으면, 다른 PC가 그 사이 되살리거나 고친 것이다. 이 경우 auto purge는 **무시한다**.
- **동시 경합**: A가 자동으로 지우는 순간 B가 되살릴 수 있다. B의 되살림 op도 같은 `trash` op를 `base`로 갖는다. 이렇게 겹치면 **되살림이 이긴다**.
  - 메모의 모습은 필드별 이긴 op(`sync_head`)만으로 다시 계산한다(`core.materialize`). 그래서 A는 자동으로 지운 메모의 `sync_head` 내용과 이미지를 **7일** 남겨 둔다. 그 사이 되살림이 오면 그것으로 되살리고, 7일이 지나면 진짜로 지운다.
  - 그 사이 이기는 op가 오면 되살린다. 7일이 지나면 진짜로 지운다.
- 동기화를 연결하지 않은 PC는 지금처럼 로컬 `deleted_at` 기준으로 30일 뒤에 지운다.

#### 직접 영구 삭제

- 사용자가 직접 "영구 삭제"나 "휴지통 비우기"를 하면 `purge` op를 만든다.
  - 받은 PC는 그 메모를 하드 삭제한다(CASCADE로 그 PC의 이전 버전도 지워진다).
  - 단, purge보다 HLC가 큰 `body` op가 있으면, 다른 PC가 삭제를 모르고 고친 것이다. 이때는 메모를 지우지 않고 **휴지통에 둔다.** 고친 글을 잃지 않기 위해서다.

### 3.5 이미지 (5단계에서 구현)

**경로 ↔ 표지** (`sync/images.py`)
- 차이 맞추기에서 본문을 비교하기 전에, 이 PC 그림 폴더 안의 경로를 `smimg:<sha256>.png`로 바꾼다. 기록(op)에는 이 표지만 들어간다. 그림 폴더 밖의 파일과 웹 주소는 그대로 둔다(다른 PC에서는 안 보인다. 붙여 넣은 그림은 모두 그림 폴더에 저장되므로 해당 없음).
- 받을 때는 표지를 이 PC의 경로로 되돌린다.
  - 같은 그림이 이 PC에 이미 있으면 그 파일을 쓴다. 원래 붙여 넣은 `img_<시각>.png`도 포함한다. 그래서 다른 PC가 글자만 고쳐도 이 PC 본문의 그림 경로는 바뀌지 않는다.
  - 없으면 받을 자리 `<그림 폴더>/<sha256>.png`로 적는다.
- 해시는 `sync_image(path, sha, size, mtime_ns)`에 기억해 두어 크기·수정 시각이 같으면 다시 읽지 않는다. 받은 그림은 이름이 곧 해시라 파일이 아직 없어도 표지로 바뀐다. 받을 자리 경로가 다시 기록을 만들지 않는다.
- 기존 파일 이름과 본문은 바꾸지 않는다. 일괄 이주가 필요 없다.

**올리기** (`engine._upload_images`)
- 기록 조각보다 **먼저** 올린다. 받는 PC가 기록을 읽을 때는 그림이 이미 있다.
- 새로 기록한 그림만이 아니라 이 PC 메모(휴지통 포함)가 쓰는 그림 전부를 본다. Drive에 없으면 올린다. 다른 PC가 안 쓰는 그림으로 보고 지웠어도 여기서 다시 올라간다.
- 같은 그림은 해시가 같아 한 번만 올라간다. 파일 이름이 달라도 마찬가지다.
- 크기에 따라 올리는 길이 갈린다.
  - 5MB 이하: `transport.write`
  - 5MB 초과: `transport.write_large`. Drive는 이어 올리기(resumable upload)로 구현한다(8단계 `DriveTransport`에 적음. 폴더 전송은 `write`와 같다).
  - 20MB 초과: 올리지 않는다. 그 해시를 `dev_` 파일의 `too_big`에 적는다. 보낸 PC는 `too_big_local`, 받은 PC는 `too_big_remote`로 안다.

**받기** (`engine._download_images`)
- 기록을 적용한 뒤, 메모가 쓰는데 이 PC에 없는 그림을 받는다. 받은 내용의 해시가 이름과 다르면 쓰지 않는다(손상).
- 임시 파일에 쓴 뒤 바꿔 넣는다. 열린 메모가 반쯤 쓴 파일을 읽지 않는다.
- Drive에 아직 없으면 넘어가고 다음 받기에서 다시 본다.
- 새로 받은 그림 목록은 `Syncer.arrived`에 남긴다. 9단계에서 창의 `images_arrived()`로 넘긴다.

**못 받은 그림의 자리 표시** (`memo_document.fill_missing_images`, `refresh_images`)
- 메모 문서를 만들 때, 받을 자리인데 파일이 없는 그림에는 회색 상자를 그림 리소스로 넣는다.
  - 기본 문구: "그림을 받는 중이에요"
  - 다른 PC가 너무 커서 못 올린 그림: "다른 PC의 그림 하나가 너무 커서 받지 못했어요"
- 본문은 먼저 보인다. 저장되는 HTML은 그대로라 자동 저장이 일어나지 않는다.
- 그림이 오면 열려 있거나 캐시된 메모 문서의 리소스를 받은 그림으로 바꿔 끼우고 다시 그린다. 저장 내용은 변하지 않는다.
- 보낸 PC의 안내("그림 하나가 너무 커서 다른 PC로 보내지 못했어요")는 9단계 UI에서 `too_big_local`을 보고 띄운다.

**안 쓰는 그림 정리** (`engine.cleanup_images`, 하루 한 번)
- "쓰인다"의 기준
  - Drive: 기록상 지금 있는 모든 메모(모든 PC, 휴지통 포함)의 본문 + 이 PC 메모의 본문
  - 이 PC 파일: 위 기준 + 이 PC의 이전 버전. 이전 버전을 되돌렸을 때 그림이 깨지지 않게 한다.
- 안 쓰이는 그림을 처음 본 시각부터 **180일**(영구 삭제 기록 보관 기간과 같다) 동안 계속 안 쓰이면 지운다. 그 사이 다시 쓰이면 세던 날짜를 버린다.
- 어느 PC든 지울 수 있다. "처음 본 시각"은 PC마다 따로 센다. 다른 PC가 아직 안 올린 기록이 그 그림을 쓰고 있었다면, 그 PC가 올릴 때 다시 올린다(위 "올리기").
- 9단계 주의: 지금 앱은 영구 삭제 때 그 메모의 그림 파일을 바로 지운다(`_delete_memo_images`). 동기화로 받은 그림은 여러 메모가 한 파일(`<sha>.png`)을 같이 쓸 수 있어서, 연결된 PC에서는 바로 지우지 말고 이 정리에 맡긴다.

### 3.6 오래 꺼져 있던 PC, 목록에서 뺀 PC (6단계에서 구현)

**문제**: 지운 기록은 180일 뒤 사라진다. 그보다 오래 동기화하지 않은 PC에만 남은 메모는, 다른 PC에서 지운 것인지 이 PC에서 새로 쓴 것인지 기록만으로는 알 수 없다.

**알아보는 법** (`engine._returning`, 동기화를 시작할 때)
- `stale`: 이 PC가 마지막으로 받은 지 170일이 넘었다(180일에서 시계 차이 여유 10일을 뺌).
- `removed`: 전에 올린 적이 있는데 Drive에 이 PC의 `dev_` 파일이 없고, 다른 PC 파일은 있다(다른 PC가 목록에서 뺐다).
- `wiped`: Drive에 아무 PC 파일도 없다(Drive 메모를 지웠다). 처음 연결처럼 기록을 비우고 전부 올린다.

**처리** (`engine._handle_return`, 받기 다음에)
- 이 PC 메모 중 아래를 모두 만족하는 것만 "다른 PC에서 지워진 메모"로 본다.
  1. 다른 PC의 메모 목록(`alive_`)에 없다.
  2. 다른 PC가 이미 받아 본 메모다. 이 PC가 만든 메모라면, 다른 PC가 받은 순번(`dev_`의 `cursors`, 빠진 PC면 이 PC가 올렸던 마지막 순번)보다 앞에 만든 것이다. 꺼져 있는 동안 새로 쓴 메모는 여기서 빠지므로 정상적으로 올라간다.
- 그런 메모는 **지우지 않고 이 PC 휴지통으로 옮긴다**. 그리고 동기화에서 뺀다(`local_only`). 그 메모의 기록과 아직 못 올린 변경도 버린다.
  - 휴지통에 있는 동안은 다른 PC로 가지 않는다. 그래서 다른 PC에서 지운 메모가 다른 PC 휴지통에 되살아나지 않고, 내용 없는 메모가 생기지도 않는다.
  - 사용자가 되살리면 새 메모처럼 전부 다시 올라간다.
  - 30일이 지나면 이 PC의 휴지통 자동 정리로 사라진다.
- 옮긴 개수를 한 번 알린다(9단계 화면): "이 PC는 오랫동안 동기화하지 않았어요. 다른 PC에 없는 메모 N개를 휴지통으로 옮겨 뒀어요. 필요하면 되살리면 돼요." (`Syncer.take_return_notice()`, 0이면 띄우지 않음)
- 추천한 점: 단순히 휴지통으로 옮기기만 하면 그 휴지통 이동이 다른 PC로 퍼진다. 그러면 이미 지운 메모가 다른 PC 휴지통에 빈 내용으로 생긴다. 그래서 "이 PC에만 두기"를 더했다. 또 메모 목록 파일로 "다른 PC에 지금 있는가"를 직접 확인하므로, 다른 PC에 아직 있는 메모를 잘못 옮기지 않는다.
- `removed`면 마지막에 이 PC의 device ID를 새로 만든다. 아직 못 올린 변경만 새 ID·새 순번으로 다시 매겨 올린다(`store.rebase_device`). 이미 올렸던 변경은 뺀 PC가 넘겨받았다(아래).

**연결된 PC 목록과 목록에서 빼기**
- `Syncer.devices()`: Drive의 `dev_` 파일에서 PC 이름, 마지막 동기화 시각, 이 PC인지를 읽는다(이 PC가 맨 앞, 나머지는 최근 순).
- `Syncer.remove_device(dev)`: 다른 PC를 목록에서 뺀다.
  1. 그 PC 기록을 끝까지 받는다. 덜 보이면(파일이 아직 안 올라옴) 아무것도 지우지 않고 실패로 돌려준다.
  2. 그 PC가 쓴 최신 값(그 PC 것인 `sync_head`)을 이 PC 기록으로 넘겨받는다(`store.adopt`). 시계와 `base`는 원래 그대로다. 원래 기록을 이미 받은 PC에는 같은 값이라 아무 일도 없고, 못 받은 PC에는 이어 쓰기가 되어 충돌 없이 들어간다.
  3. 넘겨받은 기록을 올린다.
  4. 그다음 그 PC의 `dev_`, `log_`, `snap_`, `alive_` 파일을 지운다.
- 빠진 PC가 다시 켜지면 `removed`로 처리하고(위), 새 ID로 목록에 다시 나타난다.

## 4. 동기화하는 것과 안 하는 것

| 동기화함 | 동기화 안 함 (PC별) |
|---|---|
| 메모의 제목·본문·색·글꼴·고정·휴지통 상태·만든 시각 | 이전 버전(`memo_versions`), `color_before_v2` |
| 이미지 | 바 방향(`side`), 바 너비(`tab_width`), 창 위치·크기(`window_y`, `window_width`, `window_height`, `memo_tab_height`), 로고 단추 위치(`edge_button_y`) |
| 사용자 지정 색(`user_slots`) | 화면 모드(`theme_mode`), 투명도(`window_opacity`), 앱 글꼴(`app_font_family`, `app_font_size`), 표시 방식(`display_mode`), 정렬(`sort_mode`) |
| | AI 설정 전부(`ai_*`), AI 키(keyring `memo_slide_ai`), 녹음 설정(`recording_*`), 녹음 파일 |
| | 안내·이주 표시(`guide_*`, `seen_whatsnew_version`, `paper_notice_pending`, `height_ratio_v2_migrated`), 자동 실행 |

- 동기화하지 않는 것은 막는 방식이 아니라 **허용 목록**으로 관리한다. 새 설정을 추가해도 자동으로 올라가지 않게 하기 위해서다.

## 5. 동기화 시점

| 때 | 하는 일 |
|---|---|
| 편집 후 | 마지막 변경 뒤 **5초** 조용하면 올린다. 계속 고치고 있어도 **30초**에 한 번은 올린다. 올리기 전 아직 안 올린 op 중 `(uid, f)`마다 최신 것만 남긴다. 이때 `base`는 남긴 묶음 중 가장 오래된 op의 `base`를 쓴다 |
| 주기 받기 | 앱이 켜져 있으면 **60초**마다. 바를 숨긴 채 10분 넘게 입력이 없으면 **5분**마다 |
| 바를 펼칠 때 | 바로 확인한다. 직전 확인 뒤 **10초**가 안 지났으면 건너뛴다 |
| 앱을 켤 때·절전에서 깰 때·인터넷이 돌아올 때 | 바로 받고 올린다 |
| 앱을 끌 때 | 안 올린 op가 있으면 최대 **3초** 기다려 올린다. 못 올리면 다음 실행 때 올린다(op는 로컬 DB에 있다) |
| "지금 동기화" | 바로 받고 올린다 |

**변경 확인 방법**: `changes.list`(`spaces=appDataFolder`, 저장한 `pageToken`)로 바뀐 파일만 알아낸다. 바뀐 것이 없으면 요청 **1회**로 끝난다.

**요청 수 어림** (PC 1대 기준):
- 쉬고 있을 때: 분당 1회.
- 계속 편집할 때: 분당 2~4회(올리기) + 1회(확인).
- 다른 PC 변경을 받을 때: 바뀐 파일 수만큼 더한다.
- 이 정도는 Drive API 기본 할당량(사용자별·프로젝트별 분당 한도)보다 몇 자리 작다. 정확한 한도는 Cloud 콘솔 "할당량"에서 확인해 이 문서에 적는다.

**429·5xx를 받으면**: 지수 백오프(2, 4, 8 … 최대 5분, 무작위 흔들기)로 기다린다. 그 동안에도 앱은 그대로 쓸 수 있다.

## 6. 화면 흐름 (문구는 해요체)

### 6.1 연결
- 설정 → 동기화 탭.
  - 설명: "메모를 내 Google Drive에 보관하고 다른 PC와 맞춰요. 메모는 내 Drive의 앱 전용 공간에만 저장돼요."
  - 개인정보처리방침 링크도 둔다.
- [Google 계정 연결]을 누르면 브라우저가 열리고 앱에는 "브라우저에서 허용해 주세요… [취소]"가 뜬다.
- 허용하면 브라우저에 "연결됐어요. 이 창은 닫아도 돼요."가 뜨고, 앱에는 "user@gmail.com 계정으로 연결됐어요."가 뜬다.
- 이 PC가 전에 다른 계정으로 연결된 적이 있으면(설정에 남은 이메일과 다르면) 바로 확인을 받는다.
  > **다른 계정이에요**
  > 전에는 a@gmail.com으로 연결했어요. b@gmail.com으로 연결하면 다른 PC의 메모와 따로 보관돼요.
  > [이 계정으로 연결] [취소]
  - [취소]를 누르면 받은 토큰을 바로 철회하고 저장하지 않는다.
- 5분 동안 응답이 없거나 사용자가 거부하면 "연결하지 못했어요. 다시 시도해 주세요."를 띄운다.

### 6.2 두 번째 PC에서 처음 연결
Drive에 다른 PC의 데이터가 있고, 이 PC에도 메모가 있을 때(처음 켤 때 생기는 빈 메모 하나뿐이면 묻지 않는다) 다음을 묻는다.
> **합칠까요?**
> Drive에 다른 PC의 메모가 있어요. 이 PC의 메모 N개와 합칠게요. 같은 메모가 두 개 보이면 하나를 지우면 돼요. 합치기 전에 이 PC의 메모를 백업해 둘게요.
> [합치기] [나중에]

- 서로 다른 PC에서 만든 메모는 `uid`가 달라서, 합칠 때 덮어쓰기가 일어나지 않는다. 그냥 모두 모인다.
- [나중에]를 누르면 연결을 끝내지 않고 토큰도 저장하지 않는다.

### 6.3 충돌 토스트
- 로컬 내용이 졌을 때: "다른 PC에서 같은 메모를 고쳤어요. 이 PC에서 쓴 내용은 이전 버전에 남겼어요. [보기]"
- 다른 PC 내용이 졌을 때: "다른 PC에서 고친 내용은 이전 버전에 남겼어요. [보기]"
- [보기]를 누르면 그 메모의 이전 버전 창이 열린다. 짧은 시간에 충돌이 여러 개 나면 토스트는 한 번만 띄우고, 메모 개수를 적는다.

### 6.4 상태
- 동기화 탭에는 다음을 보여 준다.
  - "마지막 동기화: 3분 전"
  - [지금 동기화] 버튼
  - 연결된 계정 이메일. 계정이 여러 개인 사람이 다른 계정으로 연결하는 실수를 막기 위해서다.
    - 로그인 때 받은 `id_token`에서 `email`만 꺼낸다. 토큰 응답은 TLS로 Google에서 바로 받은 것이라 서명 검증은 하지 않는다.
    - 이 PC의 `settings`(`sync_account_email`)에만 저장하고 화면 표시와 6.1의 계정 비교에만 쓴다. Drive에도 올리지 않고 다른 곳으로 보내지도 않는다.
    - 연결을 끊어도 지우지 않는다(다음 연결 때 비교용). 동기화 탭에 [기억한 계정 지우기]를 둔다.
  - 이 PC의 이름과 연결된 PC 목록(이름, 마지막 동기화 시각, [목록에서 빼기]). 바탕은 3.6의 `devices()`·`remove_device()`
    - 기본값은 Windows 컴퓨터 이름(`COMPUTERNAME`)이다. 사용자 이름은 넣지 않는다.
    - 동기화 탭에서 바꿀 수 있다. 바꾸면 `dev_<device>.json`을 다시 올린다.
- 연결이 안 될 때는 바 맨 아래 상태 줄에 작은 경고 아이콘을 띄운다.
  - 아이콘 툴팁: "지금은 동기화할 수 없어요. 인터넷이 돌아오면 이어서 맞출게요."
  - 오프라인 상태가 1시간 미만이면 아이콘을 띄우지 않는다.

### 6.5 연결 끊기
> **동기화를 끊을까요?**
> 이 PC의 메모는 그대로 남아요. Drive에 올린 메모는 남겨 둬요.
> ☐ Drive에 올린 메모도 지우기 (다른 PC도 더 이상 받을 수 없어요)
> [끊기] [취소]

- 순서는 다음과 같다.
  1. (체크했으면) appDataFolder 파일을 지운다.
  2. Google에 토큰 철회를 보낸다.
  3. keyring에서 토큰을 지운다.
  4. 연결 표시만 끈다. 마지막 기록(`sync_head`)과 `uid`는 남긴다. 다시 연결할 때 끊긴 동안 고친 것을 찾는 기준이다(11.5).
     - Drive의 메모도 지우기를 체크했으면 마지막 기록도 지운다. 다음 연결 때 전부 새로 올린다.
- 2번(철회)이 실패하면(오프라인 등) 3번은 그대로 하고 이렇게 안내한다. "Google에 연결을 끊었다고 알리지 못했어요. Google 계정 → 보안 → 타사 앱 연결에서 직접 지울 수 있어요. [열기]"

## 7. 실패 처리

| 상황 | 동작 |
|---|---|
| 오프라인 | 앱은 그대로 쓴다. op는 로컬 DB의 `sync_outbox`에 쌓이고 연결되면 올라간다 |
| access token 만료 | refresh token으로 조용히 다시 받는다 |
| refresh token 무효 (`invalid_grant`: 사용자가 권한 회수, 비밀번호 변경 등) | 동기화를 멈추고 상태를 "다시 연결해 주세요"로 바꾼다. 토스트를 한 번 띄우고, 바 상태 줄에 경고를 띄운다. 쌓인 op는 버리지 않는다 |
| 403 권한 부족, 저장 공간 가득 | "Drive 저장 공간이 부족해요" 등 일반화한 문구를 보여 준다. 응답 원문은 로컬 로그에만 남긴다 |
| 동기화 중 앱이 꺼짐 | 아래 원자성 규칙 때문에 아무것도 깨지지 않는다 |

**원자성 규칙**

1. op는 메모를 고칠 때 남기지 않고 **차이 맞추기**(`SyncStore.reconcile`, 11.5)로 만든다. 마지막 기록과 지금 DB를 비교해 다른 필드만 op로 만들고, op·마지막 기록·시계를 **한 트랜잭션**으로 저장한다. 고친 직후 꺼져도 다음 비교에서 다시 잡히므로 "메모는 바뀌었는데 op가 없는" 상태가 오래 남지 않는다.
2. 받은 op 적용, `sync_head` 갱신, `sync_cursor` 갱신도 한 트랜잭션으로 한다. 중간에 꺼지면 전부 취소되고 다음에 다시 받는다.
3. Drive 업로드는 파일 단위로 통째로 바뀐다. 업로드에 성공한 뒤 "올림" 표시를 하기 전에 꺼지면, 다음에 같은 op를 다시 올린다. 읽는 쪽이 PC별 순번 커서로 거르므로 문제없다.
4. 압축은 "새 파일 올림 → 목록 바꿈 → 옛 파일 지움" 순서로 한다(2.3).
5. `sync_state`의 HLC 값과 op 순번도 op 기록과 같은 트랜잭션에서 저장한다.

**보안** (전역 보안 원칙 기준)

- 토큰과 인증 코드는 로그에도 오류 메시지에도 남기지 않는다.
- loopback 서버는 `127.0.0.1`에만 연결한다. 요청은 한 번만 받고, `state`가 다르면 거부한다. 5분 뒤에는 닫는다.
- 브라우저에 보여 주는 응답 페이지에는 오류 원문을 넣지 않는다.
- 클라이언트 비밀값은 설치본에 들어간다는 전제로 다룬다. 그래도 그 값으로 남의 데이터에는 닿지 못한다. 접근하려면 사용자 본인의 동의와 PKCE를 거친 토큰이 필요하다.

## 8. 코드 구조

```
src/sync/
  core.py        op 만들기, HLC, LWW 합치기, 충돌 판정, 압축 계획 (Qt·네트워크 없음)
  store.py       로컬 DB의 동기화 테이블 읽기·쓰기 (MemoDatabase와 같은 연결)
  transport.py   Transport 약속: list_changes, read, write, delete
  local_folder.py  LocalFolderTransport: 폴더 하나를 Drive처럼 쓴다 (테스트용, 실제 앱에서도 동작)
  drive.py       DriveTransport: Drive REST v3, appDataFolder 전용
  oauth.py       loopback + PKCE 로그인, 갱신, 철회, keyring
  runner.py      QThread에서 도는 스케줄러 (5장의 시점), 상태 신호
```

- `core`는 `Transport` 약속만 안다. Drive를 몰라야 테스트에서 PC 두 대를 폴더 하나로 흉내 낼 수 있다.
- `Transport`는 구현이 두 개(로컬 폴더, Drive)라서 약속을 따로 둘 이유가 있다.
- 시계는 `core`에 함수로 넘긴다. 테스트에서 PC마다 시계를 몇 시간씩 틀어 볼 수 있게 하기 위해서다.
- `MemoDatabase`의 쓰기 메서드는 고치지 않는다. 기록은 `store.reconcile()` 한 곳에서만 만든다(11.5). 쓰기 경로마다 기록을 끼우면 하나라도 빠뜨리거나 2.0.x처럼 기록을 모르는 코드가 DB를 고칠 때 놓친다.
  - 동기화를 연결하지 않았을 때는 op를 만들지 않는다.
- HTTP는 표준 라이브러리 `urllib.request`로 한다(질문 5).
  - 필요한 요청은 몇 가지뿐이다: 토큰 발급·갱신·철회, `files.list/get/create/update/delete`, `changes.getStartPageToken/list`.
- 시험 (Google 없이):
  - `test_sync_core.py`: HLC 순서, 필드별 LWW, 동시 수정 시 진 쪽이 버전에 들어가는지, purge와 편집이 겹칠 때.
  - `test_sync_two_pcs.py`: 임시 DB 두 개와 `LocalFolderTransport` 폴더 하나로 다음 경우를 확인한다.
    - 동시 편집. 시계를 ±6시간 틀린 경우도 포함한다.
    - 고정과 편집이 겹칠 때.
    - 삭제·복원 전파.
    - 같은 이미지가 한 번만 올라가는지, 경로가 되돌려지는지.
    - 압축 뒤 늦게 켠 PC가 따라오는지.
    - 일부러 중간에 멈추게 해 본다(올림 뒤, 적용 중, 압축 중). 다시 시작하면 두 DB가 같아지는지 확인한다.
  - `test_sync_oauth.py`: 가짜 토큰 서버로 PKCE 값, `state` 거부, `invalid_grant`가 "다시 연결" 상태가 되는지 확인한다.

## 11. 기존 사용자 이주 (2.0.x → 동기화 구조)

1. **스키마 v4**: 앱을 켤 때 연결 여부와 상관없이 진행한다.
   - 바뀌기 전 DB를 `memos.db.bak-v3`로 백업한다. 2.0.0 때 만든 `memos.db.bak`은 덮어쓰지 않는다.
   - `memos`에 `uid TEXT` 열과 유일 색인을 추가한다. 비어 있는 행에는 UUID4를 채운다.
   - 동기화 테이블은 `SyncStore`가 처음 쓸 때 만든다(새 표 추가라 백업이 필요 없다). 3단계: `sync_state`, `sync_outbox`, `sync_head`, `sync_body_chain`. 4단계: `sync_cursor`. 5단계: `sync_image`. (`sync_seen_op`는 두지 않는다. 한 PC의 op는 순번대로 오므로 커서만으로 거른다.)
2. **빈 `uid`는 켤 때마다 채운다.** 사용자가 2.0.x로 되돌렸다가 다시 올리면 2.0.x가 만든 메모의 `uid`가 비어 있을 수 있다.
   - 2.0.x는 새 열과 표를 몰라도 그대로 동작한다. 열을 더하기만 했기 때문이다.
   - 다만 2.0.0은 `user_version`을 3으로 되돌린다. 그래서 이주 단계 판단에 `user_version`만 믿지 않고 열이 있는지도 함께 본다.
3. **처음 연결할 때**:
   - 연결 직전에 `memos.db.bak-sync-<날짜>`로 백업한다.
   - 휴지통을 포함한 모든 메모의 현재 상태를 op로 만든다(`created`, `body`, `color`, `font`, `pin`, `trash`). `base`는 없다. 따로 만드는 코드가 아니라 11.5의 차이 맞추기다. 마지막 기록이 비어 있으니 전부 "다름"이 된다.
   - 이미지는 해시를 계산해 올린다.
   - Drive에 다른 PC 데이터가 있으면 6.2의 "합칠까요?"를 먼저 묻는다.
4. 본문 HTML과 이미지 파일 이름은 바꾸지 않는다(3.5).
5. **기록 없이 생긴 변경을 놓치지 않기: 차이 맞추기(`reconcile`)**
   - 메모마다 "마지막으로 기록한 상태"를 `sync_head`에 둔다. 필드마다 이긴 op 전체(값 포함)라서 내용 해시보다 확실하다. 받은 op를 적용할 때도 같은 트랜잭션에서 갱신한다.
   - 차이 맞추기는 이 상태와 지금 `memos` 표를 필드별로 비교해 다른 것만 op로 만든다.
     - DB에 있는데 기록이 없으면: 새 메모 → `created`, `body`, `color` 등.
     - 기록엔 살아 있는데 DB에 없으면: 영구 삭제됨 → `purge`.
     - 휴지통 여부가 다르면: `trash`. 2.0.x가 넣은 휴지통 시각(`deleted_at`)을 그대로 쓴다.
     - 직접 만든 색(`user_slots`)도 같은 방식이다.
   - 언제 하나: 앱을 켤 때(1단계의 `uid` 채우기 바로 뒤), 연결하거나 다시 연결할 때, 올리기 직전(5장의 5초 묶음).
   - 이것으로 세 경우가 한 길로 처리된다.
     1. 처음 연결: 기록이 비어 있어 전부 올라간다(11.3).
     2. 끊었다 다시 연결(같은 계정): 끊을 때 기록을 남겨 두므로 끊긴 동안 고친 것만 올라간다. `base`도 이어져 다른 PC에서 거짓 충돌이 나지 않는다.
        - 다른 계정으로 연결하거나 Drive를 지웠으면 기록을 비우고 전부 새로 올린다.
        - 같은 계정인데 Drive에서 이 PC의 `dev_` 파일이 사라졌으면: 다른 PC 파일도 없으면(Drive 메모를 지움) 기록을 비우고 전부 새로 올리고, 다른 PC 파일은 있으면(목록에서 빠짐) 3.6대로 한다.
     3. 2.0.x로 되돌렸다 다시 올림: 2.0.x는 기록을 모르지만 `memos` 표가 달라져 있으니 켤 때 잡힌다.
   - 주의 (9단계): 연결된 PC에서는 지금의 30일 자동 정리(`cleanup_old_trash`, 로컬 시각 기준)를 끄고 `autopurge`(3.4)로 바꾼다. 그대로 두면 로컬에서 지운 메모가 차이 맞추기에서 직접 영구 삭제(`purge`)로 잡혀, 다른 PC의 되살림을 덮는다.
   - 주의 (6단계): 영구 삭제된 메모의 내용이 `sync_head`와 `sync_outbox`에 남는다. 압축 때 `purge`(직접 삭제) 메모의 `body` 값은 지우고 id·시계만 남긴다. `autopurge`는 7일 뒤에 지운다(3.4).

### 개인정보처리방침에 넣을 문장 (블로그 쪽)

> **Google Drive 동기화 (선택)**
> 설정에서 "Google 계정 연결"을 직접 누른 경우에만 동작해요. 기본은 꺼져 있어요.
> - 메모(제목, 본문, 색, 글꼴, 고정·휴지통 상태)와 메모 속 그림, 직접 만든 색, PC 이름을 **사용자 본인의 Google Drive 앱 전용 공간**에 저장해요. 이 공간은 Drive 화면에 보이지 않고, SlideMemo만 읽고 쓸 수 있어요. 개발자는 이 데이터를 볼 수 없고, 개발자 서버를 거치지 않아요.
> - 요청하는 권한은 앱 전용 공간(`drive.appdata`)과 계정 이메일 확인(`openid`, `userinfo.email`)뿐이에요. Drive의 다른 파일은 볼 수 없어요.
> - 계정 이메일은 다른 계정으로 잘못 연결하는 일을 막으려고 이 PC의 설정에만 저장하고 화면에 보여 주는 데만 써요. 어디로도 보내지 않아요.
> - 로그인 정보(갱신 토큰)는 Windows 자격 증명 관리자에 저장해요.
> - "연결 끊기"를 누르면 이 PC의 로그인 정보를 지우고 Google에 권한 철회를 요청해요. 원하면 Drive에 저장한 메모도 함께 지울 수 있어요. Google 계정 → 보안 → 타사 앱 연결에서도 언제든 권한을 지울 수 있어요.
